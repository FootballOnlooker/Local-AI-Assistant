# Local AI Assistant

🇩🇪 **Deutsche Version:** [README_DE.md](README_DE.md)

A local desktop AI assistant for German customer-service messages.

The application combines three components:

1. a local language model running through **Ollama**;
2. a fine-tuned **German DistilBERT** classifier;
3. a hybrid local **retrieval** component: exact matching for reference codes plus multilingual sentence embeddings for
   everything else.

The final Tkinter interface displays the user's message, its predicted category and confidence score, and an
AI-generated answer based on the local knowledge base.

---

## Features

- Runs locally without a cloud LLM API
- Desktop GUI built with Tkinter
- German customer-message classification
- Four categories: `Anfrage`, `Reklamation`, `Rechnung`, `Sonstiges`
- Confidence score based on the highest Softmax probability
- Local knowledge base stored as text files
- Hybrid retrieval: exact reference-code matching + multilingual sentence-embedding search over document chunks
  (`sentence-transformers`) with cosine similarity
- Multi-turn conversation memory and persistent user instructions (e.g. "answer in max. 3 sentences from now on")
- Language-matching: replies in the language of the current message (primarily German, with reliable English support)
- Context-grounded answers generated by Llama 3.2
- Standalone scripts for training, prediction, dataset inspection, and retrieval testing

---

## Architecture

```text
User message
    │
    ├──► DistilBERT classifier
    │       └──► category + confidence
    │
    └──► Hybrid retrieval
            ├──► exact reference-code match (regex)         ─┐
            └──► chunk-level sentence-embedding search        ─┤
                                                              ▼
                                                  most relevant document(s)
                                                              │
                                                              ▼
                                                    Ollama / Llama 3.2
                                                              │
                                                              ▼
                                                       grounded answer

All results are displayed in the Tkinter GUI.
```

## Part 1: Local AI Chat Assistant

### Goal

Build a desktop assistant that communicates with a locally running language model and answers customer-service questions
using local documents.

### Technologies

- Python
- Tkinter
- Ollama
- Llama 3.2:3b
- Scikit-learn

### Retrieval Bonus

Before a question is sent to the language model, the application searches the local knowledge base. The retrieval
pipeline is a **hybrid** of two strategies, in this order:

**1. Exact reference-code matching (regex).** Reference codes such as shipment, invoice, or policy numbers (`EXP-70531`,
`RE-2024-1187`, `VP-30987`) are short, rare alphanumeric tokens. In testing, semantic embeddings did not reliably
retrieve documents for these — their similarity scores landed just below the relevance threshold, since embedding models
are tuned for natural-language meaning, not exact short codes. A regex (`[A-Z]{2,5}-[0-9][0-9A-Z-]+`)
extracts any such code from the question and checks for a literal (case-insensitive) match across all knowledge
documents first. If the same code legitimately appears in more than one document, all matching documents are combined
into the context, clearly separated, rather than arbitrarily picking the first one found.

**2. Semantic search over document chunks (sentence embeddings).** If no reference code is found in the question, the
app falls back to `sentence-transformers` (`paraphrase-multilingual-MiniLM-L12-v2`). Both the model and the embeddings
are computed once at startup, not on every message.

Documents are **not** embedded as a whole — they are split into paragraph-level chunks first (`chunk_documents()`), each
chunk embedded separately, and the question is compared against chunks rather than whole documents. This was a
deliberate fix for a real, measured problem during development: the embedding model has `max_seq_length = 128`
tokens. Several knowledge documents (100-190 words, i.e. roughly 130-300 tokens after German subword tokenization)
exceeded that limit, so content near the end of a document was silently truncated and invisible to the embedding —
regardless of how important it was. Chunking keeps every unit of text safely under the limit (verified: the longest
chunk in the current knowledge base is ~91 estimated tokens) without shrinking what the LLM ultimately sees — the
**full** parent document is still returned as context once its best-matching chunk is found.

The retrieval query combines the current question with the last two user messages, so follow-up questions like "how long
would delivery *there* take?" can still be matched to the right topic without repeating the city name.

```text
knowledge documents
    └──► split into paragraph-level chunks (chunk_documents)
            └──► chunk embeddings (computed once at startup)

user question
    └──► reference code in question?
            ├─ yes ──► exact substring match across documents
            └─ no  ──► question embedding
                            └──► cosine similarity vs. chunk embeddings
                                    └──► best matching chunk
                                            └──► full parent document returned as context (if above threshold)
```

A minimum similarity threshold (`MIN_SIMILARITY = 0.35`) is used for the semantic path — calibrated on three real test
questions, not guessed: a question closely matching the document's own wording scored ~0.69; a genuinely relevant but
differently-phrased question ("I haven't received my invoice" vs. the document's more formal wording)
scored ~0.41; an unrelated question scored ~0.26. The threshold sits with margin above the irrelevant case and below
both relevant cases. If no sufficiently relevant chunk is found and no reference code matched, the application tells the
LLM explicitly that no documented information exists, instead of letting it invent an answer.

As an additional safeguard, the app also runs a small deterministic check: it extracts the cities actually documented in
`lieferung.txt` and, if a question asks about delivery to a city that isn't listed, adds a short, isolated instruction
telling the model not to invent a delivery time for it. This exists because purely prompt-based instructions ("don't
invent facts") were not 100% reliably followed by the 3B model across all test runs — this is a deliberate
reinforcement, not a full bypass of the LLM, to keep answers natural while reducing (not eliminating) the risk of
fabricated numbers for undocumented cities.

### Multi-turn Conversation Test

**Goal:** verify that the assistant (a) remembers information given earlier in a conversation and correctly resolves a
later follow-up question that refers back to it without repeating it, and (b) reliably follows a persistent behavioral
instruction ("answer in max. 3 sentences") across several subsequent turns.

**Test conversation** (5 messages in a row, `llama3.2:3b`, no message repeated):

1. `Hallo, meine Sendungsnummer lautet EXP-88213, und der Zielort ist Budapest.`
2. `Antworten Sie ab jetzt bitte immer in maximal drei Sätzen.`
3. `Wie hoch ist die Standardhaftung bei Transportschäden?`
4. `Und wie sieht es mit der erweiterten Transportversicherung aus?`
5. `Wie lange würde der Transport dorthin ungefähr dauern?` — deliberately does not repeat "Budapest", to test whether
   turn 1 is still remembered 4 turns later.

**Final result:**

| # | Assistant reply                                                                                                                                                                            | Check                                                                     |
|---|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| 1 | "Sie hat Ihre Sendungsnummer (EXP-88213) und den Zielort (Budapest) genannt."                                                                                                              | Acknowledges only, no question back, no "missing data" claim              |
| 2 | "Entschuldigung, ich werde mich daran erinnern. Die Lieferung von Sendungsnummer EXP-88213 nach Budapest wird bearbeitet. Wir werden sich um die korrekte Abholung und Lieferung kümmern." | 3 sentences, stays on topic                                               |
| 3 | "Die Standardhaftung für Transportschäden beträgt den gesetzlichen Höchstbetrag pro Kilogramm Rohgewicht der beschädigten oder verlorenen Ware."                                           | Verbatim from `garantie.txt`, no invented figures                         |
| 4 | "Die erweiterte Transportversicherung deckt den deklarierten Warenwert bis zur vereinbarten Versicherungssumme ab, Zuschlag abhängig vom Warenwert."                                       | Verbatim from `garantie.txt`                                              |
| 5 | "Die Lieferung von Sendungsnummer EXP-88213 nach Budapest wird in der Regel 1-2 Werktage dauern."                                                                                          | Correctly resolves "dorthin" → Budapest 4 turns later, without repetition |

**Bugs found and fixed while running this test** (all in `teil1/chat.py` / `teil1/retrieval.py`):

1. **Lost destination city across turns.** The retrieval query only combined the last 2 user messages; by turn 5, turn 1
   (where "Budapest" was mentioned) had fallen out of that window, so semantic search stopped finding
   `lieferung.txt` and the model wrongly claimed no delivery time was documented for Budapest, even though it is. Fixed
   with a separate, deterministic city check (`find_mentioned_documented_city()`) that scans the *entire*
   conversation — not just a small window — for a known city and injects the exact documented delivery time whenever the
   current question is actually about duration.
2. **Wrong document retrieved for unrelated follow-ups.** Combining several turns into one embedding query let an
   *earlier* topic dominate the search for a *later*, unrelated question: "Sendungsnummer EXP-88213" (turn 1) pulled in
   `rechnung.txt` (which contains a similarly-formatted example code) for turns 3–4, even though those questions were
   clearly about liability/insurance (`garantie.txt`). Fixed by searching with the current question alone first, only
   falling back to the combined multi-turn query if that alone finds nothing.
3. **Fabricated numbers.** Before the fixes above, the model invented figures not present in any document (e.g.
   "8%", "100% des Transportpreises") — a direct violation of the "don't invent facts" rule. This mostly resolved once
   retrieval pointed at the correct document; the prompt was also strengthened to explicitly forbid adding unstated
   explanatory clauses, not just unstated numbers.
4. **Rule violation on pure statements.** When the user only stated information (no question), the assistant still
   discussed "missing documentation" instead of a brief confirmation. Fixed by only attaching document context to the
   prompt when the current message actually contains a question mark, with an explicit fallback instruction reinforcing
   confirmation-only behavior otherwise.
5. **Question log polluted by irrelevant matches.** A document can be "found" by `retrieve_document()` even when it
   isn't used in the answer (see #4); `database.py`'s question log now only records `document_id` /
   `was_found_in_kb` when a document was actually part of the response.

**Known remaining limitation:** occasional small grammar slips (e.g. "Sie hat" instead of "Sie haben") and, rarely, a
mild unrequested elaboration beyond the source text. Both are inherent to a 3B-parameter local model rather than a logic
bug — confirmed by re-running the test multiple times and observing that every *deterministic* check (city, document,
figures) stayed correct while only minor wording varied.

### Reference Code Retrieval Test

**Goal:** verify that the assistant correctly finds and quotes information for reference codes that really are
documented, and — just as importantly — does **not** invent a status/answer for a plausible-looking but entirely made-up
code.

**Test questions** (each a fresh, independent question, no shared conversation):

| # | Question                                               | Code           | Documented?                    |
|---|--------------------------------------------------------|----------------|--------------------------------|
| 1 | `Zu welcher Sendung gehört die Rechnung RE-2024-1187?` | `RE-2024-1187` | Yes (`rechnung.txt`)           |
| 2 | `Was deckt die Versicherungspolice VP-30987 ab?`       | `VP-30987`     | Yes (`garantie.txt`)           |
| 3 | `Wie ist der Status der Sendung GRP-44190?`            | `GRP-44190`    | Yes (`lieferung.txt`)          |
| 4 | `Was ist mit der Sendung EXP-99999 passiert?`          | `EXP-99999`    | **No** — made up for this test |

**Result:**

| # | Retrieval                                                                                        | Assistant reply                                                                                                                                                                                |
|---|--------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | `rechnung.txt`, similarity 1.0 (exact code match)                                                | "Die Rechnung RE-2024-1187 wurde zur Sendung EXP-70531 gestellt." — verbatim from the document                                                                                                 |
| 2 | `garantie.txt`, similarity 1.0 (exact code match)                                                | "Die Versicherungspolice VP-30987 deckt den deklarierten Warenwert bis zur vereinbarten Versicherungssumme ab, Zuschlag abhängig vom Warenwert." — correct, matches the document's description |
| 3 | `lieferung.txt`, similarity 1.0 (exact code match)                                               | "Die Sendung GRP-44190 wurde am Montag abgeholt und ist laut Sendungsverfolgung am Dienstagvormittag beim Empfänger eingetroffen." — verbatim from the document                                |
| 4 | `lieferung.txt`, similarity 0.54 (semantic fallback only — **no** exact code match, as expected) | "Es gibt keine dokumentierte Information über die Sendung EXP-99999." — correctly refuses to invent a status                                                                                   |

All four responses passed on the first run, without any further code changes: the exact-match regex path (see
"Retrieval Bonus" above) reliably finds real codes with similarity `1.0`, and for the made-up code it correctly falls
through to the semantic-only path, which stays below the confidence needed to state a specific answer — so the model is
told explicitly that no documented information exists rather than being left to guess.

### English Language Support

The assistant is supposed to reply in the language of the current message (rule 7 in `SYSTEM_PROMPT`). In testing,
an English question about content that is only documented in German (`Could you tell me what the extended transport
insurance covers?`) produced a broken, still-German sentence fragment instead of a coherent English answer — the
language rule alone was not reliably followed once German document text entered the context.

**Fix:** a lightweight heuristic (`ENGLISH_MARKERS` / `GERMAN_MARKERS` in `teil1/chat.py`) detects when the current
message looks like English (English function words present, German ones absent) and, only in that case, adds one
additional, explicit system instruction telling the model to answer exclusively in English and translate the facts
without changing or adding content. This is a purely prompt-level fix — no changes to retrieval, no translation
model, no new logic path — just one conditional extra instruction in the prompt sent to Ollama.

**Verification:** the same English question now returns "The extended transport insurance covers the declared value
of the goods up to the agreed-upon insurance amount. ..." — correct language, grounded in `garantie.txt`. All German
test questions from both scenarios above were re-checked against the heuristic and correctly do **not** trigger it,
confirming German behavior is unaffected.

## Part 2: German Text Classification

### Goal

Fine-tune a transformer model to classify German customer messages.

### Categories

- `Anfrage`
- `Reklamation`
- `Rechnung`
- `Sonstiges`

---

### Dataset

The dataset consists of hand-written sentence templates, each used **exactly once** (verified programmatically at the
time of creation, not just claimed):

- 180 German text examples
- 4 balanced categories
- 45 examples per category
- no missing values
- no duplicate rows
- **100% unique templates** — confirmed by normalizing cities/reference codes to placeholders and checking for
  collisions; there are none

An earlier version of this dataset (800 examples) reused the same sentence structure with only the city or reference
code swapped, sometimes up to 10 times. That caused a misleadingly perfect 100% test accuracy, because random splits
could place near-identical sentences on both sides of train/test. `train.py` uses `StratifiedGroupKFold` to guard
against this structurally regardless of how the dataset is built, and the dataset itself was additionally rewritten to
be genuinely unique at the source — belt-and-suspenders rather than relying on either fix alone.

---

### Training Pipeline

1. Load and validate the CSV dataset.
2. Convert category names to numerical IDs.
3. Create a template-group-aware stratified train/test split (`StratifiedGroupKFold`), preventing near-duplicate
   template variants from leaking between train and test.
4. Convert the data to Hugging Face Dataset objects.
5. Tokenize the texts.
6. Fine-tune `distilbert-base-german-cased`, up to 6 epochs with early stopping (patience 2) and automatic selection of
   the best checkpoint by accuracy.
7. Evaluate the model on the test set, including a per-class precision/recall/F1 report and a saved confusion matrix
   image (`teil2/confusion_matrix.png`).
8. Save the model and tokenizer locally.

---

### Training Results

These results are from the final dataset (180 fully unique examples, `StratifiedGroupKFold` split) — no template leakage
between train and test. The accuracy is close to the very first exploratory run on a smaller 200-example dataset
(87.50%), which is a good independent sanity check that the model is genuinely generalizing rather than memorizing
sentence templates.

| Parameter               |                          Value |
|-------------------------|-------------------------------:|
| Base model              | `distilbert-base-german-cased` |
| Dataset size            |                            180 |
| Classes                 |                              4 |
| Training samples        |                            144 |
| Test samples            |                             36 |
| Max epochs configured   |                              6 |
| Epochs actually trained |                            6.0 |
| Batch size              |                              8 |
| Learning rate           |                         `2e-5` |
| Training time           |                       2.10 min |
| Evaluation loss         |                         0.6385 |
| Test accuracy           |                     **86.11%** |

Results may vary slightly between systems and training runs. See `teil2/confusion_matrix.png` for a visual breakdown of
which categories get confused with which.

**Per-class report:**

| Category    | Precision | Recall | F1-score | Support |
|-------------|----------:|-------:|---------:|--------:|
| Anfrage     |      0.88 |   0.78 |     0.82 |       9 |
| Reklamation |      0.89 |   0.89 |     0.89 |       9 |
| Rechnung    |      0.88 |   0.78 |     0.82 |       9 |
| Sonstiges   |      0.82 |   1.00 |     0.90 |       9 |

`Sonstiges` has perfect recall (every actual `Sonstiges` message was found) but lower precision — confirmed by the
confusion matrix (`teil2/confusion_matrix.png`): 2 of the `Rechnung`-confusions come from `Anfrage` examples that were
misclassified as `Sonstiges`, which is the single largest source of error and explains both anomalies at once (`Anfrage`
recall 7/9, `Sonstiges` precision 9/11). The remaining errors are scattered rather than concentrated:
`Rechnung` had one example each misclassified as `Anfrage` and as `Reklamation`, and `Reklamation` had one example
misclassified as `Rechnung`. No category is confused specifically and consistently with another single category —
`Sonstiges`, being the most semantically diffuse label, is the main attractor for borderline cases.

Results may vary slightly between systems and training runs.

## Installation

### 1. Clone the repository

```bash
git clone https://github.com/FootballOnlooker/Local-AI-Assistant.git
cd Local-AI-Assistant
```

### 2. Create a virtual environment

```bash
python -m venv .venv
```

Activate it on Windows:

```bash
.venv\Scripts\activate
```

Activate it on Linux or macOS:

```bash
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Download the Ollama model

```bash
ollama pull llama3.2:3b
```

Ensure that Ollama is running. Depending on the installation, it may start automatically. Otherwise run:

```bash
ollama serve
```

### 5. Train the classifier

The trained model is not stored in Git because model files are large.

```bash
python teil2/train.py
```

This creates:

```text
teil2/model/final_model/
```

### 6. Run the application

```bash
python -m teil1.main
```

## Limitations

- The classifier is trained on a small manually created dataset.
- The confidence score is the highest Softmax probability and is not a guarantee that the prediction is correct.
- The semantic retrieval (sentence-transformers) is tuned for meaning over exact wording; very rare domain jargon (e.g.
  specific logistics terms not covered by the model's training data) may not be matched as sharply as common vocabulary.
  Exact reference codes bypass this via a separate regex-based lookup (see Retrieval Bonus above).
- The local 3B LLM (`llama3.2:3b`) does not follow purely prompt-based instructions with 100% reliability, especially
  when several rules apply at once (conversation memory, sentence-count limits, language matching, and "don't invent
  facts" simultaneously). Where this mattered most in testing (undocumented delivery cities), a small deterministic
  code-level check was added as reinforcement — this reduces but does not eliminate the risk of occasional fabricated
  answers.
- Ollama and the trained classifier must be available locally before the GUI can run.
- The GUI currently performs model calls synchronously, so it may briefly appear unresponsive while the local LLM
  generates an answer.

---

## Possible Improvements

- Expand and diversify the classification dataset.
- Run model calls in a background thread to keep the GUI responsive.
- For maximum reliability on undocumented-data cases, the deterministic city check could be extended into a full bypass
  (skip the LLM entirely and return a fixed message) instead of just reinforcing the prompt — considered during
  development but intentionally not implemented, to keep answers natural rather than templated.
- Add automated tests for retrieval and classification.
