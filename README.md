# Local AI Assistant

🇩🇪 **Deutsche Version:** [README_DE.md](README_DE.md)

A local desktop AI assistant for German customer-service messages.

The application combines three components:

1. a local language model running through **Ollama**;
2. a fine-tuned **German DistilBERT** classifier;
3. a hybrid local **retrieval** component: exact matching for reference
   codes plus multilingual sentence embeddings for everything else.

The final Tkinter interface displays the user's message, its predicted category and confidence score, and an
AI-generated answer based on the local knowledge base.

---

## Features

- Runs locally without a cloud LLM API
- Desktop GUI built with Tkinter
- German customer-message classification
- Four categories: `Anfrage`, `Reklamation`, `Rechnung`, `Sonstiges`
- Confidence score based on the highest Softmax probability
- Local knowledge base stored as text files
- Hybrid retrieval: exact reference-code matching + multilingual
  sentence-embedding search (`sentence-transformers`) with cosine similarity
- Multi-turn conversation memory and persistent user instructions
  (e.g. "answer in max. 3 sentences from now on")
- Language-matching: replies in the language of the current message
  (primarily German, with reliable English support)
- Context-grounded answers generated by Llama 3.2
- Standalone scripts for training, prediction, dataset inspection, and retrieval testing

---

## Architecture

```text
User message
    │
    ├──► DistilBERT classifier
    │       └──► category + confidence
    │
    └──► Hybrid retrieval
            ├──► exact reference-code match (regex)         ─┐
            └──► sentence-embedding search (if no code)     ─┤
                                                              ▼
                                                  most relevant document(s)
                                                              │
                                                              ▼
                                                    Ollama / Llama 3.2
                                                              │
                                                              ▼
                                                       grounded answer

All results are displayed in the Tkinter GUI.
```

## Part 1: Local AI Chat Assistant

### Goal

Build a desktop assistant that communicates with a locally running language model and answers customer-service questions
using local documents.

### Technologies

- Python
- Tkinter
- Ollama
- Llama 3.2:3b
- Scikit-learn

### Retrieval Bonus

Before a question is sent to the language model, the application searches the local knowledge base. The retrieval
pipeline is a **hybrid** of two strategies, in this order:

**1. Exact reference-code matching (regex).** Reference codes such as shipment, invoice, or policy numbers
(`EXP-70531`, `RE-2024-1187`, `VP-30987`) are short, rare alphanumeric tokens. In testing, semantic embeddings did
not reliably retrieve documents for these — their similarity scores landed just below the relevance threshold, since
embedding models are tuned for natural-language meaning, not exact short codes. A regex (`[A-Z]{2,5}-[0-9][0-9A-Z-]+`)
extracts any such code from the question and checks for a literal (case-insensitive) match across all knowledge
documents first. If the same code legitimately appears in more than one document, all matching documents are combined
into the context, clearly separated, rather than arbitrarily picking the first one found.

**2. Semantic search (sentence embeddings).** If no reference code is found in the question, the app falls back to
`sentence-transformers` (`paraphrase-multilingual-MiniLM-L12-v2`). Both the model and the document embeddings are
loaded once at startup, not on every message. Cosine similarity is computed between the question and each document.
The retrieval query combines the current question with the last two user messages, so follow-up questions like "how
long would delivery *there* take?" can still be matched to the right topic without repeating the city name.

```text
knowledge documents
    └──► sentence-transformer document embeddings (computed once at startup)

user question
    └──► reference code in question?
            ├─ yes ──► exact substring match across documents
            └─ no  ──► sentence-transformer question embedding
                            └──► cosine similarity
                                    └──► best matching document (if above threshold)
```

A minimum similarity threshold (`MIN_SIMILARITY = 0.55`) is used for the semantic path — calibrated empirically
(a clearly relevant question scored ~0.69, an unrelated question ~0.26). If no sufficiently relevant document is
found and no reference code matched, the application tells the LLM explicitly that no documented information exists,
instead of letting it invent an answer.

As an additional safeguard, the app also runs a small deterministic check: it extracts the cities actually documented
in `lieferung.txt` and, if a question asks about delivery to a city that isn't listed, adds a short, isolated
instruction telling the model not to invent a delivery time for it. This exists because purely prompt-based
instructions ("don't invent facts") were not 100% reliably followed by the 3B model across all test runs — this is a
deliberate reinforcement, not a full bypass of the LLM, to keep answers natural while reducing (not eliminating) the
risk of fabricated numbers for undocumented cities.

## Part 2: German Text Classification

### Goal

Fine-tune a transformer model to classify German customer messages.

### Categories

- `Anfrage`
- `Reklamation`
- `Rechnung`
- `Sonstiges`

---

### Dataset

The dataset was created manually and contains:

- 200 German text examples
- 4 balanced categories
- 50 examples per category
- no missing values
- no duplicate rows

---

### Training Pipeline

1. Load and validate the CSV dataset.
2. Convert category names to numerical IDs.
3. Create a stratified train/test split.
4. Convert the data to Hugging Face Dataset objects.
5. Tokenize the texts.
6. Fine-tune `distilbert-base-german-cased`, up to 6 epochs with early stopping
   (patience 2) and automatic selection of the best checkpoint by accuracy.
7. Evaluate the model on the test set, including a per-class precision/recall/F1
   report and a saved confusion matrix image (`teil2/confusion_matrix.png`).
8. Save the model and tokenizer locally.

## Installation

### 1. Clone the repository

```bash
git clone https://github.com/FootballOnlooker/Local-AI-Assistant.git
cd Local-AI-Assistant
```

### 2. Create a virtual environment

```bash
python -m venv .venv
```

Activate it on Windows:

```bash
.venv\Scripts\activate
```

Activate it on Linux or macOS:

```bash
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Download the Ollama model

```bash
ollama pull llama3.2:3b
```

Ensure that Ollama is running. Depending on the installation, it may start automatically. Otherwise run:

```bash
ollama serve
```

### 5. Train the classifier

The trained model is not stored in Git because model files are large.

```bash
python teil2/train.py
```

This creates:

```text
teil2/model/final_model/
```

### 6. Run the application

```bash
python -m teil1.main
```

## Limitations

- The classifier is trained on a small manually created dataset.
- The confidence score is the highest Softmax probability and is not a guarantee that the prediction is correct.
- The semantic retrieval (sentence-transformers) is tuned for meaning over exact wording; very rare domain jargon
  (e.g. specific logistics terms not covered by the model's training data) may not be matched as sharply as common
  vocabulary. Exact reference codes bypass this via a separate regex-based lookup (see Retrieval Bonus above).
- The local 3B LLM (`llama3.2:3b`) does not follow purely prompt-based instructions with 100% reliability, especially
  when several rules apply at once (conversation memory, sentence-count limits, language matching, and "don't invent
  facts" simultaneously). Where this mattered most in testing (undocumented delivery cities), a small deterministic
  code-level check was added as reinforcement — this reduces but does not eliminate the risk of occasional
  fabricated answers.
- Ollama and the trained classifier must be available locally before the GUI can run.
- The GUI currently performs model calls synchronously, so it may briefly appear unresponsive while the local LLM
  generates an answer.

---

## Possible Improvements

- Expand and diversify the classification dataset.
- Run model calls in a background thread to keep the GUI responsive.
- For maximum reliability on undocumented-data cases, the deterministic city check could be extended into a full
  bypass (skip the LLM entirely and return a fixed message) instead of just reinforcing the prompt — considered
  during development but intentionally not implemented, to keep answers natural rather than templated.
- Add automated tests for retrieval and classification.
